# 这笔账：压缩到底贵在哪

这不是论文。就是我自己拿本机日志算的一笔账，算账的工具在 [`bench/`](../bench/README.md)，你可以用自己机器上的日志重算一遍。

## 先说结论

平时会话很便宜：缓存命中率 99.20%（3,515 次请求、9.97 亿 prompt token）。但官方每压一次，模型会被要求把大约 **55 万 token 的历史重新读一遍**，按新内容的价格收钱。55 万 token 大概是一本 400 页的书，每压一次就重读一遍。

同一个会话里压了三次。三次加起来，额外输入约占这个会话全部输入成本的 **5.3%**；只用 `deterministic` 模式的话能降到 **1.2%**。

## 三次压缩的实测

| turn | 压缩前 prompt | 摘要调用（缓存 / 未命中 / 输出） | 压缩后 prompt | 发布未命中 | 总计 eq. | 占该会话输入 |
| --- | --- | --- | --- | --- | --- | --- |
| 22 | 726,882 | 0 / 552,771 / 4,124 | 189,833 | 179,977 | 733,734 | 1.77% |
| 47 | 724,803 | 9,856 / 562,954 / 5,059 | 171,536 | 161,680 | 726,605 | 1.76% |
| 83 | 729,572 | 9,856 / 549,132 / 3,206 | 180,230 | 170,374 | 721,477 | 1.74% |

"总计 eq." 是把缓存读取按新读的 10% 折算后的输入量。压缩结束后的第一次请求必然要重读新前缀，那部分任何改写历史的方案都躲不掉。

## 为什么明明缓存是热的，它还是重读

我不信"缓存过期"这个解释，所以查了压缩前那一次请求：

| turn | 距上次请求 | 上次请求命中率 |
| --- | --- | --- |
| 22 | 12.8 秒 | 99.93% |
| 47 | 0.1 秒 | 99.85% |
| 83 | 1.1 秒 | 99.07% |

缓存是热的。但摘要请求只接上了开头 9,856 个 token，后面全断。原因在"重放"这件事上：压缩时 harness 把历史重新拼成一个请求发给模型，这个请求和当时真正发出去的请求不完全一样——真实请求里有些东西日志没记（请求期拼进去的内容）。拼出来的东西跟缓存里的对不上，缓存就从那里断了。

## 我试过让它变便宜，没成

我最开始的想法是让抽取调用也吃上缓存。做不到，原因就是上面那条。所以现在：

- 想省钱，就用 `deterministic`，压缩时完全不调模型。
- 想保质量，就用 `extract`，成本跟官方持平，别指望更便宜。

我不想在 README 里写"省 75%"，因为它只在 `deterministic` 下成立，那是另一个取舍。

## 三种选择的账

| 选择 | 模型调用 | 每次自动压缩的额外输入 | 相对官方 | 出来的东西 |
| --- | --- | --- | --- | --- |
| 官方摘要 | 1 次，重读约 55 万 | 约 72 万 | 1× | 模型写的摘要，没有出处 |
| 本插件 `extract` | 1 次，同样重读 | 约 72 万 | ≈1× | 逐字引文 + 结构证书 |
| 本插件 `deterministic` | 不调 | 约 17 万 | ≈0.25× | 结构筛出来的原文片段 |

（`deterministic` 的发布尺寸会跟官方摘要略有差别，这里按同量级算。）

## 质量上的差别

成本只是账的一半。另一半是：官方摘要丢了一句话，你事后查不出来。

| 问题 | 官方摘要 | 本插件 |
| --- | --- | --- |
| "端口是 8080"这种细节会被悄悄丢掉吗 | 会，而且没人能发现 | 关键约束钉成支座，丢了就拒绝发布，有测试覆盖 |
| 这句话是哪来的 | 不知道，是模型重写的 | 每条都要求逐字引用原文，对不上就不收 |
| 压缩失败会怎样 | 抛错，可能没有 checkpoint | 退到纯本地渲染，再退到官方摘要，总有 checkpoint |
| 同样的输入会得到同样的结果吗 | 看模型发挥 | 会，逐字节一致 |

官方摘要实测产出 1,728 到 5,131 token 的散文。本插件的 checkpoint 有预算（默认 6,000 token），且只出现能核验的内容。

## 另外两个数

**剪枝是亏的。** 官方 preset 里还挂着工具结果剪枝器。三轮剪枝一共"省"了 141,041 token，代价是后面请求多读 1,675,192 token，差不多 12 倍。所以本插件自己不做剪枝。

**空闲之后的手动压缩是真冷。** 有一次 `/compact` 距上次请求 49 分钟，摘要调用 331,799 token 全部未命中。这个躲不掉，缓存确实过期了。我把它单独列出来，不和上面那 55 万混在一起。

## 数字怎么算的、怎么自己验

数据是 Harness 本来就会写的会话日志（`session*.jsonl.zstd`）。只读用量记录和压缩标记，不读对话内容，会话名做哈希。

```bash
npm test                                   # 80 条离线断言，不需要装 Harness
node bench/report.mjs                      # 算本机所有会话
node bench/report.mjs <目录> --format md   # 生成同款表格
```

测试里能看到的：伪造或转述的引文会被拒；丢支座会被拒；无法接地的结构会报奇异；不能缩小源的 checkpoint 会被拒；抽取失败会退化成零模型渲染；`deterministic` 模式从不调用模型；同一批内容渲染结果逐字节相同。

装好插件后还能跑一次活体自检：`GET /compaction-continuum/selftest` 会告诉你钩子有没有生效，加 `?test=extract` 会用合成数据真跑一次抽取，返回 `units=30 candidates=33 kept=33 certificate={...}`。

## 这些结论不靠谱的地方

- 三次自动压缩来自同一个长会话。单次事件是实测，但样本就这么大。你要是有更多日志，欢迎贴结果。
- `extract` 跟官方"成本持平"是推的：同样重放、同样发布。不是同一个会话跑两遍的 A/B——压缩对单个会话是单向的，做不了。
- `deterministic` 更便宜，但质量比 `extract` 差，它没有语义抽取，只是结构筛选。
- "缓存命中按未命中 10% 计价"是价格假设，`--hit-ratio` 可以改。
- 让 `extract` 也便宜的办法是让重放跟线上请求逐字节一致。需要日志里没有的东西，目前做不到，写在路线图里。
