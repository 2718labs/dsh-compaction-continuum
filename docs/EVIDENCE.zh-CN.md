# 证据：为什么需要这个插件（说人话版）

> 先给结论，再给数字，最后给复现方法。technically-minded 的读者可以直接跳到文末的「技术附录」。

## 一句话

官方压缩每次都会让模型把**约 55 万 token 的历史重新读一遍**，这笔输入费本来可以不花（实测缓存没接上）。本插件要么把这步变成可选（`deterministic`：零模型调用），要么把这次调用的产物变成**可核验的压缩结果**（`extract`），而不是一段没法查证的摘要。

## 先看这三个数

| 场景 | 额外输入成本（token） | 说明 |
| --- | --- | --- |
| 官方一次自动压缩 | **约 72 万** | 其中约 55 万是"重读历史"，约 17 万是压缩后必然发生的重读 |
| 本插件 `deterministic` 模式 | **约 17 万** | 不调用模型，只付那 17 万 → **约省 3/4** |
| 同一会话压缩 3 次的总账 | **占该会话输入成本 5.3%** | 用 `deterministic` 可降到 **1.2%** |

> 换算一下：55 万 token ≈ 一本 400 多页的书。"重读一遍"是字面意思——模型真的会把这些内容再读一次，按未命中价计费。

## 为什么官方压缩这么贵（用白话讲）

1. 模型服务商按"这次新读了多少内容"收钱。之前读过的上下文有缓存，接着读就便宜（实测这个长会话的稳态命中率是 **99.20%**）。
2. 官方压缩的做法是：拼一个"把对话再给模型看一遍"的请求，让它写摘要。实测这个请求**只接上了缓存开头 9,856 个 token**，后面的 55 万 token 全部被当成新内容、按全价计费。
3. 这不是偶然：三次自动压缩前的那一次请求，命中率分别是 99.93% / 99.85% / 99.07%，间隔只有 12.8 / 0.1 / 1.1 秒——缓存明明还是热的，摘要调用却接不上。
4. 原因在于"重放式摘要"本身：它拼出来的请求和刚才那次真实请求不完全一样（有些只存在于请求当时的东西，日志里没有），所以缓存从中间断掉。

**本插件 `extract` 模式用的是同样的重放方式，所以在这件事上不省钱，我们也不假装省钱。** 我们能做的是把这笔调用变成可选（`deterministic`），或者把它花在更好的产物上（`extract`）。

## 三种选择，直白对比

| 选择 | 模型调用 | 每次自动压缩的额外输入 | 相对官方 | 压缩出来的东西 |
| --- | --- | --- | --- | --- |
| 官方摘要（现状） | 1 次，重读约 55 万 | 约 72 万 | 1× | 模型自由撰写的摘要，没有出处 |
| 本插件 `extract` | 1 次，同样重读 | 约 72 万 | ≈1× | 逐字引文 + 结构证书（每条都能对回原文） |
| 本插件 `deterministic` | **0 次** | 约 17 万 | **≈0.25×** | 结构筛选出的原文片段，无模型参与 |

所以"为什么需要它"有两个不同的答案：

- **想省钱** → 用 `deterministic`，把压缩里最贵的那次模型调用直接去掉。
- **想保质量** → 用 `extract`，成本与官方持平，但压缩结果可核验、可审计、关键约束丢失时**拒绝发布**。

## 质量差别（这才是主要价值）

| 问题 | 官方摘要 | 本插件 |
| --- | --- | --- |
| 会不会悄悄丢掉"必须用 A 方案""端口是 8080""这个字段不能改"这类约束？ | 会，且无人能发现 | 关键约束/锚点被钉为"支座"；丢失时拒绝发布（有测试覆盖） |
| 能不能查证某个说法来自哪里？ | 不能，是模型重写的散文 | 能，每条都要求逐字引用原文，对不上就丢弃 |
| 压缩失败时会发生什么？ | 抛错，会话可能没有 checkpoint | 三级兜底：结构编译 → 零模型渲染 → 官方摘要，永远有 checkpoint |
| 同样的输入会不会得到同样的结果？ | 不会，看模型发挥 | 会，确定性渲染逐字节一致 |

实测官方摘要产出 1,728–5,131 token 的散文；本插件的 checkpoint 有预算上限（默认 6,000 token），且只出现能核验的内容。

## 另外两个实测发现

- **剪枝是亏的**：桌面 preset 挂着官方的工具结果剪枝器。三剪枝轮次一共"省"了 141,041 token，却导致后续请求多读 **1,675,192 token**（约 12 倍）。所以本压缩器自己不做任何剪枝。
- **空闲后手动压缩是真冷**：一次距上次请求 49 分钟的手动压缩，摘要调用 331,799 token 全部未命中；这部分任何设计都躲不掉（缓存确实过期了）。我们把它单独列出，不和"本可避免的 55 万"混在一起。

## 这些数字怎么来的？你自己也能复现

- 数据源：Harness 自己写的会话日志（`session*.jsonl.zstd`）。只读用量记录和压缩标记，**不读对话内容**；会话名做哈希，不泄露路径。
- 工具：仓库里的 [`bench/`](../bench/README.md)，无第三方依赖。
- 复现：

```bash
npm test                                   # 80 条离线断言，不需要装 Harness
node bench/report.mjs                      # 统计你本机所有会话
node bench/report.mjs <目录> --format md   # 生成同类表格
```

- 契约测试（`npm test`）：伪造/转述的引文会被拒；丢失支座会被拒；无法接地的结构会报奇异；不能缩小源的 checkpoint 会被拒；抽取失败会退化为零模型渲染；`deterministic` 模式从不调用模型；同一批内容渲染结果逐字节相同。
- 活体自检（装好插件后）：`GET /compaction-continuum/selftest` 会报告后端钩子是否生效；`?test=extract` 会用它跑一次真实合成摘要，输出 `units=30 candidates=33 kept=33 certificate={...全部为 true}`。

## 老实说局限

- 三次自动压缩来自**同一个**长会话；单次事件是实测，但样本不大。欢迎用 `bench` 跑你自己的日志并贴出结果。
- `extract` 与官方"成本持平"是结构性论证（同样重放、同样发布），不是同一会话跑两遍的 A/B——压缩是单向操作，做不到。
- `deterministic` 更便宜，但质量低于 `extract`（没有语义 atom，只有结构筛选）。
- "缓存命中按未命中价 10% 计"是价格假设，可用 `--hit-ratio` 改。
- 真正能让 `extract` 也变便宜的办法是让抽取请求和线上请求逐字节一致；这需要拿到日志里没有的请求期信息，已列入路线图，当前**做不到**。

<details>
<summary>展开：字段定义与口径</summary>

- 成本单位是 **miss-equivalent 输入 token** = 未命中输入 + 0.1 × 缓存读取。用 `--hit-ratio` 改这个 0.1。
- "摘要调用"指 `compaction/summary` 事件里记录的模型调用用量。
- "发布未命中"指压缩结束后的第一次请求里按未命中计费的输入（任何改写历史的压缩都躲不掉）。
- "占该会话输入"= (摘要调用 + 发布) / 该会话全部 miss-equivalent 输入。
- 会话标签是目录名哈希；同一台机器上稳定，跨机器不可比。
- 总计样本：25 个会话、3,515 次请求、997,002,631 prompt token，稳态命中率 99.20%。
- 数据来自 DeepSeek Harness `0.2.1-rc.5` 桌面版（`deepseek-account` / `deepseek-flash`）。

</details>
