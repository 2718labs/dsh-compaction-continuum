# 证据

本文只回答一个问题：**为什么需要一个本插件这样的压缩后端，而不是官方摘要？** 下面的每个数字都能用 [`bench/`](../bench/README.md) 从已记录会话日志复现，不依赖任何我们无法公开的基准。

## 结论速览

在 DeepSeek Harness `0.2.1-rc.5` 桌面版（provider `deepseek-account` / `deepseek-flash`，价格模型：缓存命中 = 0.1 × 未命中）上，实测 **25 个会话、3,515 次已完成请求、997,002,631 prompt token**：

| 发现 | 实测值 |
| --- | --- |
| 稳态前缀缓存命中率 | **99.20%**（单会话 95.2% – 99.7%） |
| 官方一次自动压缩的成本 | **≈721k – 734k miss-equivalent**（3 次事件） |
| ↳ 其中摘要调用 | **≈549k – 563k 未命中输入**（缓存读取 0 – 9,856 token） |
| ↳ 其中发布重读 | ≈162k – 181k miss-equivalent |
| 压缩前一次请求的缓存状态 | 命中 99.07% – 99.93%，距压缩 0.1 – 12.8 秒 |
| 工具结果剪枝（3 轮） | 释放 141,041 token，造成 **1,675,192 miss-equivalent** 重读 |
| 本插件 `extract` 模式 | 同样一次调用、同样的重放形状 → **成本持平**，但产物可核验、带证书 |
| 本插件 `deterministic` 模式 | **零模型调用** → 每次压缩省掉 ≈549k–563k（实测事件上约 4× 便宜） |

官方摘要自己的重放**并不能**还原线上请求的前缀：即使紧跟在一次命中 99.85% 的请求之后，它的摘要调用也只命中 **9,856 token**（system/tools 头部），其余全部按新输入计费。这是压缩成本的主要部分，也正是本插件把它变成可选的原因。

## 方法

- 输入：Harness 本来就会写的持久会话日志（`session*.jsonl.zstd`）。只读取 `assistant/message` 的 usage 记录与 `compaction/*` 标记事件；除已发布摘要的长度外，不分析任何消息内容。
- 成本单位：**miss-equivalent 输入 token** = `未命中输入 + 0.1 × 缓存读取`。输出 token 单独报告，不混入输入成本。
- 压缩解剖：对每个 `compaction/start`…`compaction/end` 括号，取 start 之前最后一次请求与 end 之后第一次请求；摘要调用自身的 usage 记在 `compaction/summary` 上，发布重读就是那次请求的未命中输入。
- 剪枝：把连续的 `compaction/prune` 标记归为一轮；若该轮在下次请求前紧跟着一次压缩，则该轮标记为不可归因并剔除。
- 会话标签是哈希；本文不出现路径、会话 id 或内容。

复现：

```bash
# 本机日志
node bench/report.mjs --format md

# 任意导出的会话目录
node bench/report.mjs <session-root> --format md
```

## 1. 基线：缓存就是预算

| 会话 | 请求数 | prompt token | 命中缓存 | 未命中 | 命中率 |
| --- | --- | --- | --- | --- | --- |
| s-3e456bb3 | 874 | 387,283,144 | 384,347,520 | 2,935,624 | 99.24% |
| s-571cf6f7 | 371 | 121,480,662 | 121,145,472 | 335,190 | 99.72% |
| s-07b44f00 | 237 | 85,896,733 | 85,124,096 | 772,637 | 99.10% |
| s-6e5ce206 | 208 | 59,863,020 | 59,692,416 | 170,604 | 99.72% |
| s-f52bb728 | 171 | 29,906,043 | 29,691,520 | 214,523 | 99.28% |
| **全部 25 个会话** | **3,515** | **997,002,631** | **989,058,176** | **7,944,455** | **99.20%** |

长会话活在前缀缓存上。任何引入缓存分歧的后端都要直接付账——这是本项目所有决策的度量基准。

## 2. 官方压缩的主要成本是一次"冷"的摘要调用

同一个 874 请求会话里的三次自动压缩：

| turn | 压缩前 prompt | 压缩后 prompt | 释放 | 摘要调用（缓存 / 未命中 / 输出） | 发布未命中 | 总成本 eq. | 占该会话输入 |
| --- | --- | --- | --- | --- | --- | --- | --- |
| 22 | 726,882 | 189,833 | 537,049 | 0 / 552,771 / 4,124 | 179,977 | 733,734 | 1.77% |
| 47 | 724,803 | 171,536 | 553,267 | 9,856 / 562,954 / 5,059 | 161,680 | 726,605 | 1.76% |
| 83 | 729,572 | 180,230 | 549,342 | 9,856 / 549,132 / 3,206 | 170,374 | 721,477 | 1.74% |

而压缩之前那一次请求本身都是热的：

| turn | 距上次请求 | 上次请求命中率 |
| --- | --- | --- |
| 22 | 12.8 秒 | 99.93% |
| 47 | 0.1 秒 | 99.85% |
| 83 | 1.1 秒 | 99.07% |

所以那 ≈550k token 的未命中**不是**缓存过期。摘要请求重放的是持久会话前缀，而线上请求携带了持久日志无法还原的**请求期材料**：命中的部分止于 system/tools 头部（9,856 token），其后全部按新输入计费。本插件 `extract` 模式使用的是同样的重放形状，因此 `extract` 模式**只主张成本持平，不主张省钱**。

第二个案例是一次空闲后的手动 `/compact`，展示另一半限制——真正的缓存过期：

| 压缩前 prompt | 压缩后 prompt | 摘要调用（缓存 / 未命中 / 输出） | 发布未命中 | 总成本 eq. | 占该会话输入 |
| --- | --- | --- | --- | --- | --- |
| 333,341 | 19,174 | 1,920 / 331,799 / 9,516 | 8,422 | 340,221 | 10.73% |

任何后端都躲不掉冷缓存。后端能回答的问题是：它是否**必须**做那次调用。

## 3. `deterministic` 模式省掉的正是这一项

模型调用是昂贵且已证明会冷的那部分。`mode: deterministic` 下压缩器**零模型调用**，发布结构选择后的逐字 checkpoint。在实测的自动压缩事件上，这去掉了 549k–563k 未命中摘要输入，只剩发布重读：

| 模式 | 模型调用 | 发布 | 每次自动压缩合计 | 相对官方 |
| --- | --- | --- | --- | --- |
| 官方摘要 | ≈549k–563k 未命中 | ≈162k–181k | ≈721k–734k | 1.00× |
| continuum `extract` | 同样重放形状（结构上会冷） | ≈162k–181k | ≈721k–734k | ≈1.00× |
| continuum `deterministic` | **无** | ≈162k–181k（含 checkpoint 尺寸差） | **≈165k–185k** | **≈0.25×** |

这是诚实的成本叙事：本插件的优势不是"更聪明的摘要"，而是**把摘要变成可选**。

## 4. 为什么不是剪枝

桌面 preset 还挂着官方 tool-result-pruner。同一会话里三次可归因的运行：

| seq 区间 | 标记数 | 遮蔽 token | 释放 | 下次请求未命中 | 发布成本 eq. |
| --- | --- | --- | --- | --- | --- |
| 2828–2858 | 16 | 73,256 | 72,475 | 629,037 | 631,443 |
| 5226–5246 | 11 | 39,346 | 36,174 | 493,166 | 512,814 |
| 7314–7334 | 11 | 37,336 | 32,392 | 512,797 | 530,935 |
| **合计** | 38 | 149,938 | **141,041** | — | **1,675,192** |

释放 141k token 花了 1.68M miss-equivalent——即使把释放的 token 当作未来的缓存命中来定价，缓存分歧也是释放量的 ~12 倍。本压缩器因此不做任何剪枝。（7449–7451 的第四条标记紧邻一次压缩，被标记为不可归因而非错误归因。）

## 5. 插件到底发布什么，以及如何被验证

实测经济学说明模型调用应当是**可选**的；真正让后端值得用的是 checkpoint 的内容：

| 属性 | 官方摘要 | 本插件 |
| --- | --- | --- |
| checkpoint 内容 | 自由散文，实测 3,459 / 2,460 / 1,728 / 5,131 token | 带引文的 atom + 结构选择的原文，受预算约束 |
| 溯源 | 无 | 每个 atom 必须逐字引用来源；核验不过的丢弃 |
| 锚点与未关闭事项 | 可能被静默丢弃 | 钉为支座；丢失时拒绝发布 |
| 确定性 | 取决于模型 | 确定性渲染；同一批 atom 逐字节相同 |
| 零模型选项 | — | `mode: deterministic` |
| 失败行为 | 抛错，无 checkpoint | 结构 → 确定性渲染 → 官方摘要 |
| 审计 | 无 | 审计 JSON 随发布写入日志；`/context_status` 可读 |

契约证据（全部离线，无需 Harness —— `npm test`）：

- 结构内核、流水线、基准工具共 **80 条断言**。
- 拒绝类测试：转述或编造的引文被拒；丢失支座的方案被拒；无法接地的结构被报告为奇异；不能缩小源的 checkpoint 被拒。
- fail-open 测试：垃圾抽取退化为确定性渲染；抽取器抛错同样退化；`deterministic` 模式从不调用模型；同一批 atom 渲染逐字节一致。
- 活体自检（`GET /compaction-continuum/selftest`）：preset 平面后端报告 `backendUsesHookedSummarize: true`；`?test=extract` 通过它跑一次真实合成摘要：
  `units=30 candidates=33 kept=33 certificate={"supportsPreserved":true,"selectionConsistent":true,"condensationExact":true,"reconstructionError":0}`。

## 6. 局限

- 三次自动压缩来自**同一个**长会话。单事件数字是实测；"deterministic 约 4× 便宜"是这些数字的算术推论，不是第二个实验。
- `extract` 模式的"持平"是结构性论证（同样重放、同样发布），不是同一会话上的活体 A/B——压缩对单个会话是单向操作，真正的 A/B 需要同一会话跑两遍。
- 价格模型 `命中 = 0.1 × 未命中` 对齐 provider 公布的缓存折扣；可用 `--hit-ratio` 换假设重跑。
- 任何压缩都要付一次发布重读：改写历史就会改变前缀。可控的只有**发布尺寸**与**模型调用**。
- 冷摘要调用的根因是从测量推断的（命中止于 system/tools 头部）；真正导致分歧的请求期材料不可持久化，因而无法直接恢复。让抽取请求与线上请求逐字节一致是路线图项。
